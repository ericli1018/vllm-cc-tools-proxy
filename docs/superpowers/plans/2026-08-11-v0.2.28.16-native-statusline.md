# V0.2.28.16 Native StatusLine Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Keep the existing 30-second Claude-facing SSE heartbeat while adding a Claude Code native `statusLine` that can refresh once per second from read-only per-session Proxy telemetry.

**Architecture:** The existing ProgressStream remains the liveness channel and continues emitting localized 30-second heartbeat text. RuntimeTelemetry gains bounded per-session request state and a read-only `GET /cc-tool-proxy/status/<session-id>` endpoint. A standalone Claude Code status-line client reads `session_id` from Claude Code stdin, queries the Proxy using `CC_TOOL_PROXY_URL` or `ANTHROPIC_BASE_URL`, and prints the localized server-rendered status line; Claude Code's own `refreshInterval` owns the animation cadence.

**Tech Stack:** Node.js 22+, built-in HTTP/fetch APIs, Anthropic Messages-compatible SSE, Claude Code command statusLine.

## Global Constraints

- Version is exactly `0.2.28.16`.
- Existing `PROGRESS_HEARTBEAT_MS` behavior remains active and defaults to 30000 ms.
- Revert the unsuccessful v0.2.28.15 carriage-return live-line rendering to newline-appended heartbeat history.
- Native statusLine is additive; it never replaces or suppresses SSE heartbeat progress.
- Status endpoint exposes telemetry only and never request prompts, model response text, tool arguments, or secrets.
- statusLine supports `zh-TW`, `zh-CN`, `en-US`, `ja-JP`, and `ko-KP`, with unknown locale falling back to `en-US`.
- statusLine polling must not create Base vLLM, Vision, Compact, WebFetch Processor, or Language Processor requests.
- No Proxy-wide Base/Managed admission queue is reintroduced.
