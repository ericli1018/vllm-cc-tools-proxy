# V0.2.14 Recovery Routing Design

## Goal

Prevent the proxy from prematurely terminating Claude Code's multi-step agent workflow when a Base model response contains thinking-only output or malformed protocol text without a valid next action.

## Scope

V0.2.14 changes only managed-response recovery routing. It does not alter WebSearch/WebFetch execution, WebFetch Processor behavior, protocol diagnostic file storage, media processing, or the managed round limit.

## Recovery routes

### Final-channel recovery

Use only when the thinking-only response is conservatively classified as a completed user-facing answer. The classifier requires substantial structured answer content and rejects any explicit continuation, search, verification, tool, or next-step intent.

The recovery request is short-context, disables tools, disables tool choice, and asks the model to move the supplied malformed answer into visible text without adding facts.

### Continuation recovery

Use for all other invalid no-tool responses, including:

- unfinished reasoning;
- next-step planning;
- missing visible output;
- ambiguous thinking-only content;
- protocol leakage where completion cannot be established safely.

The recovery request preserves the original tools and tool choice. It keeps the original conversation and evidence, then asks the model to produce exactly one valid next action: a tool call when more work is needed, or a visible final answer when complete.

## Loop integration

A recovered response is processed by the same normal dispatch path as an ordinary Base response:

- managed WebSearch/WebFetch calls are executed by the proxy;
- non-managed Read/Bash/Edit/Task calls are returned to Claude Code;
- visible text is returned as the final response;
- a second invalid recovery response is rejected without an unbounded recovery loop.

The recovery call does not consume a managed-tool round by itself. A managed tool emitted by recovery is executed in the current round and the next Base request advances to the next managed round.

## Diagnostics

Existing V0.2.13 diagnostic files remain. Recovery events add:

- `recovery_route`;
- `tools_preserved`;
- answer-classification signals;
- recovery response disposition.

No response snippets are restored to the main log.

## Safety and compatibility

- Conservative classification favors continuation over premature finalization.
- Final-channel recovery is the only route that removes tools.
- Continuation recovery never appends malformed model text to history.
- At most one recovery call is allowed for one invalid Base response.
- Existing event names remain available, with route metadata added where possible.
