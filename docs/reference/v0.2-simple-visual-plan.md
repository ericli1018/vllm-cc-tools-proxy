# VLLM-CC-TOOLS-PROXY V0.2 簡化架構規劃

日期：2026-08-05  
狀態：設計提案，尚未進入實作  
基線：V0.1.0

## 1. 核心結論

V0.2 建議改成：

```text
Claude Code
→ vllm-cc-tools-proxy
   ├─ Local Poppler：PDF 文字、頁面資訊、頁面渲染
   ├─ Local ImageMagick：圖片正規化、縮放、切圖
   ├─ SearXNG：WebSearch
   ├─ awesome-web-fetch：WebFetch
   ├─ Visual vLLM：PDF 頁面、圖片、OCR、圖表與視覺分析
   └─ Base vLLM：主推理、Claude Code Tool Calling
```

V0.2 預設只啟動一個 Proxy 容器。

```text
不再內建：
document-parser container
image-parser container
ocr-service container
bootstrap.sh
git pull 更新流程
```

容器每次啟動時，在 Compose 的 inline `command` 內：

```text
安裝必要 OS packages
→ git clone 最新 main
→ 啟動 Proxy
```

## 2. 三種架構比較

### A. 維持 V0.1 多 Sidecar

```text
Proxy
Document Parser
Image Parser
OCR Service
Visual vLLM
Base vLLM
```

優點：

- 故障域與資源可獨立。
- 各服務可水平擴充。

缺點：

- Compose 複雜。
- ENV 過多。
- 同一 Repository 被多個容器 clone。
- Tesseract、Vision、Image Parser 有功能重疊。
- 不符合本次「傻瓜模式」方向。

### B. 單一 Proxy＋Visual vLLM，建議採用

```text
Proxy
├─ 本機 Poppler
├─ 本機 ImageMagick
├─ Visual vLLM
└─ Base vLLM
```

優點：

- Compose 最簡單。
- 文件與圖片都走同一 Visual Pipeline。
- 不需要 OCR、圖片、文件三組服務 URL。
- Visual vLLM 同時處理 OCR、Layout、圖表與圖片語意。
- 只需保留五個 vLLM ENV。

缺點：

- Proxy 容器需安裝 Poppler 與 ImageMagick。
- Visual vLLM 不可用時，掃描 PDF 與圖片無法完整處理。
- PDF 頁面渲染會使用 Proxy CPU 與暫存空間。

### C. 所有文件直接送 Visual vLLM

```text
PDF／Image Base64
→ Visual vLLM
```

不建議。

原因：

- OpenAI-compatible Vision Endpoint 通常接受圖片，不直接接受 PDF。
- 大型 PDF 必須拆頁、限制頁數與批次。
- 無法安全控制切圖、解析範圍與 Context。
- 原生文字 PDF 使用 Vision OCR 會浪費資源且降低文字準確度。

## 3. Docker Compose 啟動方式

### 3.1 移除

```text
deploy/bootstrap.sh
REPOSITORY_URL
REPOSITORY_BRANCH
AUTO_UPDATE
SYSTEM_PACKAGES
proxy-source volume
document-parser-source volume
image-parser-source volume
ocr-source volume
```

### 3.2 Compose 直接使用 `git clone`

概念：

```yaml
services:
  vllm-cc-tools-proxy:
    image: node:22-bookworm-slim
    command:
      - /bin/sh
      - -lc
      - |
        apt-get update
        apt-get install -y --no-install-recommends \
          git ca-certificates poppler-utils imagemagick
        rm -rf /workspace/vllm-cc-tools-proxy
        git clone --depth 1 --branch main \
          https://github.com/ericli1018/vllm-cc-tools-proxy.git \
          /workspace/vllm-cc-tools-proxy
        cd /workspace/vllm-cc-tools-proxy
        exec node src/index.js
```

行為：

```text
docker compose up
→ 每次建立／重建 Container 都重新 clone
→ 不執行 git pull
→ 不保留舊 Source Tree
```

更新方式：

```bash
docker compose pull
docker compose up -d --force-recreate
```

實際 Source 更新只需要：

```bash
docker compose restart
```

但為避免 Container 內殘留狀態，文件建議使用：

```bash
docker compose up -d --force-recreate
```

### 3.3 取捨

這個做法比 `bootstrap.sh` 簡單，但有兩項代價：

- 每次 Container 重建都需連線 GitHub。
- 每次啟動都會執行 `apt-get`，啟動速度較慢。

這是「只使用官方 Node.js Image、不要 Dockerfile、不要外部啟動 Script」必然的成本。

## 4. 保留的 vLLM ENV

基本 `.env` 只保留：

```env
VLLM_BASE_URL=http://host.docker.internal:8000
VLLM_BASE_API_KEY=

VLLM_VISION_URL=http://host.docker.internal:8001
VLLM_VISION_MODEL=Qwen/Qwen3-VL-30B-A3B-Instruct
VLLM_VISION_API_KEY=
```

### 4.1 明確語意

#### `VLLM_BASE_URL`

主文字模型的 Server Root：

```text
http://vllm-text:8000
```

Proxy 自動呼叫：

```text
POST {VLLM_BASE_URL}/v1/messages
POST {VLLM_BASE_URL}/v1/messages/count_tokens
```

#### `VLLM_BASE_API_KEY`

送給 Base vLLM：

```http
Authorization: Bearer <VLLM_BASE_API_KEY>
```

空值時不送 Authorization。

#### `VLLM_VISION_URL`

Visual vLLM 的 Server Root：

```text
http://vllm-vision:8000
```

Proxy 自動呼叫：

```text
POST {VLLM_VISION_URL}/v1/chat/completions
```

#### `VLLM_VISION_MODEL`

Visual Endpoint 的 served model name。

#### `VLLM_VISION_API_KEY`

送給 Visual vLLM：

```http
Authorization: Bearer <VLLM_VISION_API_KEY>
```

## 7. 圖片處理流程

Claude Code Request：

```json
{
  "type": "image",
  "source": {
    "type": "base64",
    "media_type": "image/png",
    "data": "..."
  }
}
```

Proxy：

```text
Base64 size validation
→ MIME／magic validation
→ ImageMagick auto-orient
→ pixels／dimensions limit
→ resize 到 Visual vLLM 上限
→ 建立 source_id
→ 呼叫 Visual vLLM
→ 執行有界切圖循環
→ 取得視覺 Markdown
→ 原 image block 替換為 text block
→ 送 Base vLLM
```

替換結果：

```xml
<visual_asset
  source_id="image-1"
  media_type="image/png"
  width="1920"
  height="1080"
  visual_model="Qwen/Qwen3-VL-30B-A3B-Instruct">

<analysis>
...
</analysis>

</visual_asset>
```

原始 Base64 不會送給 Base vLLM。

## 8. PDF 處理流程

### 8.1 共通前處理

```text
PDF Base64
→ decoded bytes limit
→ PDF magic validation
→ private temporary directory
→ pdfinfo
→ pdftotext -layout
→ pdftoppm／pdftocairo render
```

### 8.2 原生文字 PDF

```text
pdftotext
→ 保留每頁文字
→ 頁面圖片送 Visual vLLM
→ Visual vLLM 補充：
   圖表
   流程圖
   電路圖
   UI
   圖片
   表格 layout
→ 合併文字與視覺結果
```

不要求 Visual Model 重做所有 OCR。

### 8.3 掃描 PDF

```text
每頁渲染為圖片
→ 分批送 Visual vLLM
→ Visual vLLM 執行 OCR、Layout、圖片分析
→ 必要時要求切圖
→ 合併頁面 Markdown
```

### 8.4 大型 PDF

不將全部頁面放入單一 Vision Request。

建議固定內建：

```text
每批最多 4 頁
每份 PDF 最多 100 頁（default profile）
每批獨立完成
最後合併
```

較大的文件仍使用既有 `RESOURCE_PROFILE` 控制。

Visual vLLM 只負責：


最後任務仍由 Base vLLM 執行。

## 10. 局部切圖機制

### 10.1 內部工具

Visual vLLM 只取得一個 Proxy-owned Tool：

```text
request_image_crop
```

Schema：

```json
{
  "name": "request_image_crop",
  "description": "Request a higher-resolution crop when important text or visual relations are unclear.",
  "parameters": {
    "type": "object",
    "properties": {
      "source_id": {
        "type": "string"
      },
      "bbox": {
        "type": "array",
        "items": {
          "type": "integer",
          "minimum": 0,
          "maximum": 1000
        },
        "minItems": 4,
        "maxItems": 4,
        "description": "[left, top, right, bottom] in normalized 0-1000 coordinates"
      },
      "purpose": {
        "type": "string",
        "maxLength": 200
      }
    },
    "required": [
      "source_id",
      "bbox",
      "purpose"
    ]
  }
}
```

### 10.2 為何用 0–1000 座標

- 不依賴實際圖片 pixels。
- 圖片縮放後仍可定位。
- 容易驗證。
- 對 Vision Model 較容易輸出。

### 10.3 執行流程

```text
Initial Vision Request
→ Vision Model 回 request_image_crop
→ Proxy 驗證 source_id 與 bbox
→ ImageMagick 裁切原始高解析圖
→ 放大 2 倍
→ 將 crop image 送回同一 Vision Conversation
→ Vision Model 完成分析
```

### 10.4 有界限制

固定內建，不放 ENV：

```text
最多 2 個 Crop Round
每個 Round 最多 4 個 Crop
每份 Asset 最多 6 個 Crop
Crop 最小區域為原圖 1%
Crop 最大放大倍率 4×
禁止越界座標
禁止任意檔案路徑
禁止由 Visual Model 指定 shell command
```

### 10.5 無界循環防護

```text
Round 0：原圖
Round 1：第一次 Crop
Round 2：最後一次 Crop
Round 3：禁止
```

超限時：

```text
停止切圖
→ 要求模型以現有證據完成
→ warning=visual_crop_limit_reached
```

## 13. 是否使用 Structured Output

### 建議 V0.2

Crop Request 使用原生 Tool Calling：

```text
request_image_crop
```

最後分析使用普通 Markdown Text。

不強制：

```text
response_format=json_schema
XGrammar
Structured Output FSM
```

原因：

- 降低 DFlash／XGrammar／大型 JSON 的相容性風險。
- Vision Endpoint 只需要一個簡單 Tool。
- 最終 Markdown 不需嚴格 JSON Grammar。

## 18. Error Policy

| 情況 | 回應 |
|---|---|
| Text PDF，Vision 未設定 | 使用原生文字繼續，附加 warning |
| 圖片，Vision 未設定 | HTTP 422，`vision_endpoint_required` |
| 掃描 PDF，Vision 未設定 | HTTP 422，`vision_endpoint_required` |
| Visual vLLM 401／403 | HTTP 502，`vision_auth_failed`，不可無界重試 |
| Visual vLLM timeout | 最多一次 Recovery，之後停止 |
| Crop bbox 無效 | Tool Result error，允許模型修正一次 |
| Crop 超過限制 | 停止 Crop，以現有資訊完成 |
| Client disconnect | 取消 Poppler、ImageMagick、Visual vLLM、Base vLLM |
| Visual 分析失敗但 native text 可用 | 降級使用 native text，明確 warning |
| Visual 分析失敗且無 native text | HTTP 422 或 502，依失敗類型 |

## 21. 最終建議

採用方案 B：

```text
一個官方 Node.js Proxy Container
+
Base vLLM
+
Visual vLLM
```

V0.2 的核心應從：

```text
多個解析 Sidecar
```

```text
Proxy 做安全拆解與圖片操作

Base vLLM 做主推理與 Claude Code Tool Calling
```
